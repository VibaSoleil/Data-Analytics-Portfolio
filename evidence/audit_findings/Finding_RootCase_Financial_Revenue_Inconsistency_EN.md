# FINDING 13 — Inconsistency in File Paths and Locations as the Main Root Cause

**Status: ROOT CAUSE CONFIRMED — HIGH CONFIDENCE**

Based on all evidence obtained, the creation and distribution flow of the cleaned dataset can now be clearly traced.

### Proven Flow

**Raw Data**

`Perusahaan_db1.csv`

↓

**n8n**

`WF_03_Data_Quality_Validation_n8n`

↓

**HTTP Request**

`/clean`

↓

**Python FastAPI**

`main.py`

↓

**Python generates**

`/app/OUTPUT/Company_Data_Cleaned_n8n.csv`

↓

**FileResponse returned to n8n**

↓

**Convert to File**

↓

**n8n Read/Write Files from Disk**

↓

**n8n saves**

`/app/OUTPUT/DATA/Company_Data_Cleaned_n8n.csv`

### Identified Issue

The same logical cleaned dataset has several names/locations used within the project ecosystem:

* `Company_Cleaned_n8n.csv`
* `Company_Data_Cleaned_n8n.csv`
* `/app/OUTPUT/`
* `/app/OUTPUT/DATA/`

In addition, examination of the downstream scripts shows that several processes use different paths.

For example:

`/app/OUTPUT/Company_Cleaned_n8n.csv`

while other scripts use:

`/app/OUTPUT/DATA/Company_Data_Cleaned_n8n.csv`

and several other processes explicitly refer to:

`/app/OUTPUT/DATA/Company_Data_Cleaned_n8n.csv`

### Additional Evidence from Source Code

Examination of the downstream scripts identified the use of:

`/app/OUTPUT/Company_Cleaned_n8n.csv`

in several analysis scripts.

Other scripts use:

`/app/OUTPUT/DATA/Company_Data_Cleaned_n8n.csv`

This demonstrates **inconsistency in path and filename references across system components**.

### Root Cause

**The main Root Cause is inconsistency in the output-file architecture between the Python API, n8n workflow, and downstream processing.**

The Python API generates the cleaned dataset in one location, n8n then writes the result again to another location, while downstream scripts use several different paths and filenames for the same logical dataset.

This results in:

1. Multiple physical files for the same logical dataset.
2. A data path that is difficult to trace consistently.
3. No single **canonical output file** explicitly established as the primary source for all downstream processes.
4. Increased risk of using legacy artifacts or files from different locations.
5. More complex reconciliation between processes because filenames and output paths are not standardized.

### Conclusion Boundaries

Based on the latest evidence, **the inconsistency in paths and filenames has been proven to be an architectural/data-lineage issue**.

However, because the three files examined currently have the **same MD5**, there is no evidence that the difference in their locations **directly caused differences in their contents at present**.

Therefore, the confirmed Root Cause is:

**inconsistency in the management and referencing of the cleaned dataset**, not evidence that each physical copy has different contents.

### Final Conclusion of Finding 13

Based on source-code inspection, workflow export, physical file verification, file-content examination, and MD5 verification, the **Root Cause has been confirmed with a high level of confidence (High Confidence)** in the area of **data lineage and output-file management**.

The main issue is no longer simply the question of **who created the file**, because the producer has been successfully identified.

The main issue is:

**how one logical cleaned dataset is managed through multiple output paths and filenames without one consistent canonical source.**
